# Automated Versioning and Release SystemThis project uses GitHub Actions to automatically handle version bumping and releases based on branch naming conventions.## 🌟 How It WorksWhen you merge a Pull Request to the `master` branch, the system automatically:1. Detects the version type based on your branch name2. Bumps the version in `package.json`3. Creates a Git tag4. Generates a GitHub release with release notes5. Builds and attaches the project artifacts## 📋 Branch Naming ConventionsUse these branch naming patterns to trigger automatic versioning:### Major Version Bump (1.0.0 → 2.0.0)```feature/major/your-feature-namefeat/major/your-feature-name```**Use for:** Breaking changes, major new features, API changes### Minor Version Bump (1.0.0 → 1.1.0)```feature/minor/your-feature-namefeat/minor/your-feature-name```**Use for:** New features, enhancements that are backward compatible### Patch Version Bump (1.0.0 → 1.0.1)```feature/patch/your-feature-namefeat/patch/your-feature-namefix/patch/your-bug-fixhotfix/patch/your-hotfixbugfix/patch/your-bugfix```**Use for:** Bug fixes, small improvements, patches### Release (No Version Change)```release/your-release-name```**Use for:** Creating a release from the current version without bumping## 🚀 Usage Examples### Example 1: Adding a Major Feature```bashgit checkout -b feature/major/new-authentication-system# Make your changesgit push origin feature/major/new-authentication-system# Create PR to master → This will bump from 1.2.3 to 2.0.0```### Example 2: Adding a Minor Feature```bashgit checkout -b feat/minor/user-profile-enhancements# Make your changesgit push origin feat/minor/user-profile-enhancements# Create PR to master → This will bump from 1.2.3 to 1.3.0```### Example 3: Bug Fix```bashgit checkout -b fix/patch/navigation-bug# Make your changesgit push origin fix/patch/navigation-bug# Create PR to master → This will bump from 1.2.3 to 1.2.4```### Example 4: Hotfix```bashgit checkout -b hotfix/patch/critical-security-fix# Make your changesgit push origin hotfix/patch/critical-security-fix# Create PR to master → This will bump from 1.2.3 to 1.2.4```### Example 5: Create Release Without Version Bump```bashgit checkout -b release/stable-release# Make your changes (documentation, etc.)git push origin release/stable-release# Create PR to master → This will create a release with current version```## 📊 What Happens When PR is Merged1. **Branch Analysis**: The workflow reads your branch name2. **Version Calculation**: Determines the appropriate version bump3. **Package Update**: Updates `package.json` with new version4. **Git Operations**: Commits the version change and creates a tag5. **Build Process**: Runs `yarn build` to create production artifacts6. **Release Creation**: Creates a GitHub release with:   - Auto-generated release notes   - PR information and changelog   - Build artifacts (zip file)7. **GitHub Pages**: Your existing Pages deployment runs automatically## 📝 Release NotesThe system automatically generates release notes that include:- PR title and description- Branch information- Version change details- Full changelog link- Build artifacts## ⚠️ Important Notes1. **Branch naming is case-sensitive** - use exactly the patterns shown above2. **Only merged PRs trigger versioning** - draft or closed PRs won't trigger releases3. **Branches not matching patterns** will merge normally without version changes4. **Version bumps are committed back to master** with `[skip ci]` to avoid loops5. **Each release includes a zip file** with the built project## 🔧 Manual ReleaseIf you need to create a release manually:```bashnpm version patch  # or minor, majorgit push origin master --tags```## 📁 Generated ArtifactsEach release includes:- **Source code** (automatic GitHub feature)- **Build artifacts**: `portfolio-build-vX.X.X.zip`- **Release notes** with complete change information## 🎯 Best Practices1. **Use descriptive branch names** beyond the required pattern:   - ✅ `feature/minor/user-dashboard-enhancements`   - ❌ `feature/minor/stuff`2. **Write clear PR descriptions** - they become part of release notes3. **Follow semantic versioning principles**:   - **Major**: Breaking changes   - **Minor**: New features (backward compatible)   - **Patch**: Bug fixes4. **Test thoroughly** before merging to master## 🏷️ Current WorkflowsThe project now includes these automated workflows:- `automated-versioning.yml` - Main versioning and release workflow- `build-release.yml` - Builds and packages artifacts for releases- `static.yml` - Existing GitHub Pages deployment (unchanged)---Happy versioning! 🎉
